Kakeya AI Prototype

一个面向三维 Kakeya 型问题的研究原型：把几何建模、体积下界估计与 AI 辅助推理做成可运行、可独立复核的计算实验。 数值主干保持纯函数，C++ 内核缺失时自动回退 NumPy；候选路径由 surrogate 与 LLM 打分，并统一经过共用守卫； 每一步都可以落成带哈希链的 .kpt 证明轨迹。

Overview

把数学想法变成可复跑的计算实验

项目围绕三维 Kakeya 型问题，提供四层能力：几何结构建模表达管状集合、方向与几何关系；数值估计与验证评估体积下界与实验结果； 启发式搜索与推理用 surrogate 与 LLM 打分器探索候选路径；调度与资源建模把提问拆成可测的调度主链，并配套芯片预算模型。

定位边界 研究原型

README 明确把这套代码定位为“研究原型”和“实验平台”，而不是生产级系统。它适合研究、教学与算法验证，不承诺工程 SLA，也不把数值复核等同于形式化证明。

Numeric Spine

六段主干：从管集到可复核轨迹

主干每一步都对应一次真实的数值计算。加速与 AI 打分是可关闭的横向旁路：关掉任何一条，主干仍能跑通，只是更慢或少了搜索建议。

01

几何原语

Primitives

用显式的管、方向与 shading 表达输入，让后续每一步都有可序列化的几何对象。

02

非聚集检查

Wolff Axioms

检查管族是否满足后续推理所需的非聚集条件——这是 Move 能否应用的前提。

03

方向对齐分解

Grains

把管集按方向对齐拆成 grains，为局部修正与体积估计提供可操作的几何单元。

04

三条 Move

Moves

Move #1 / #2 / #3 对应不同的几何修正路径；先计算条件，再决定哪一条真正可执行。

05

证明路径搜索

Proof Orchestrator

“状态 → 检查 → 选择 Move → 应用 → 再检查”的主循环，直到成功或预算耗尽。

06

轨迹与复核

Trace Format

把几何输入、每步指纹与哈希链写入 .kpt；verify 可独立重算并逐步定位差异。

可选的横向旁路包括 grains_fast / grains_cpp 加速、volume 体积校验，以及 surrogate_scorer / model_router 等 AI 打分路径；它们不改变主干语义。

AI Reasoning

打分可以关闭，采纳必须过守卫

在 Move 选择这条路径上，AI 只提出候选，不直接改写几何状态。所有来源的建议都要经过同一套条件检查与有效性守卫；被拦下的建议退回启发式，并显式记入 notes。

候选搜索：surrogate + LLM

仓库提供 surrogate 打分器与 LLM 打分器两条实验路径，以及 beam search、两阶段打分、专家路由等接口；LLM 侧通过本地 Ollama 运行，README 示例使用 qwen3.5:4b。

打分器给出的候选只有在 gap 超过阈值时才会进入守卫；没有 Ollama 时，相关用例会自动跳过或打桩，测试仍可运行。

共用守卫：什么才算“生效”

条件检查 m1_ok / m2_ok / m3_ok 在三条路径之前统一计算。候选必须通过 _scored_action_allowed：条件已满足的 Move 会被拒绝，同状态下试过且指标逐位不变的 Move 也会被拒绝。

被守卫拦下不是错误——它退回启发式，但会显式记录，避免把“给了答案但没用”统计成“生效”。

仓库记录的一次真实修复 修复前数据

在共用守卫修复前，surrogate 选出的 Move 有效率只有 12%（36 次空转 / 5 次有效），低于启发式的 33%。原因是前两条打分路径绕过了条件检查，空转建议也被算进了“生效”。修复后，条件检查前置、建议统一过守卫，被拦下的建议会进入 notes。

Scheduling

从提问到计划，只调度、不执行

调度主链把“提问 → 子问题 → 模块/资源 → 执行顺序 → 计划”拆成可测试的步骤。chip_model 判断算力还是带宽受限，predict_schedule 依据单核墙钟选择线程数。

01

提问

Query

接收自然语言提问，作为调度主链的输入。

02

拆子问题

Decompose

按关键词拆成 SubQuestion[]，每个子问题带自己的 ModuleKind。

03

逐子问题规划

Plan Query

消费 chip_model 与 predict_schedule，产出“模块 + 后端 + 线程数”的 TaskPlan。

04

执行顺序

Execution Order

拓扑分层后按核预算裁定：并发需求超订就串行，否则并行或让 host 任务重叠。

05

计划

SchedulePlan

只产出计划，不执行计算；真正的执行仍走 accel 与各个 kernel。

expert_router 是另一条分工线：它决定“用哪个模型回答”，不决定“调哪些计算模块”。架构清单是芯片/调度/内核的单一真源，scheduler_flow.mmd 由清单生成，手改会被守门测试判红。

kakeya-kpt head   trace.kpt --json   # 只读头部：规模 / 结论 / 参数
kakeya-kpt steps  trace.kpt -n 10    # 流式逐步读出

轨迹的浮点按 float.hex() 参与哈希，逐位精确；哈希链能定位到具体哪一步被改动，而不是只报“整个文件坏了”。

Honest Boundaries

这些说法，项目自己先划清

研究原型，不是生产系统 定位

README 的原始定位就是“研究原型”与“实验平台”。它用于研究、教学和算法验证，不承诺生产环境的性能、稳定性或运维能力。

哈希链只保证完整性，不是认证 安全边界

.kpt 的哈希链能防意外损坏、传输错误和事后悄悄改数；但没有密钥，有动机的攻击者可以改内容后重算整条链。要抵抗这种场景需要签名，项目明确说明暂未实现，也不假装实现。

独立复核 ≠ 形式化证明 证据边界

verify 会重新计算每一步的体积下界并与文件比对，这是“解释器”的自洽检查，不是 Lean 之类的形式化证明。数值结论可以复跑，但不因此自动获得定理地位。

调度器只出计划，不执行计算 职责边界

SchedulePlan 描述模块、后端、线程数与执行顺序，但不触发实际计算。真正的执行仍由 accel 与各个 kernel 完成，避免“计划”和“执行”混成一个不可审计的黑箱。
